## Быстрый старт

Полноценный SQL IDE одной командой, без клонирования репозитория и без сборки:

```bash
# Docker (рекомендуется)
docker run -p 3000:3000 ghcr.io/libredb/libredb-studio:latest

# либо через Node.js 24+ (без Docker)
npx @libredb/studio
```

Затем откройте **http://localhost:3000**. При первом запуске пароль администратора выводится в лог, без единого файла конфигурации.

> Если браузер обращается к серверу не через localhost и не по HTTPS (например, `http://192.168.x.x:3000` в локальной сети), дополнительно понадобится `AUTH_COOKIE_SECURE=false`. Без этого health-check проходит нормально, а вход в систему тихо не срабатывает и возвращает обратно на экран логина.

Нужны Helm, Homebrew, Snap, winget или deb/rpm? Смотрите [способы установки](#установка) ниже.

## Зачем ещё один инструмент для баз данных

Вы поднимаете Postgres на управляемой платформе, и через сорок секунд он готов.

Потом вы хотите заглянуть внутрь. И тут приходится открывать порт наружу, ставить десктопный клиент и копать SSH-туннель, или просто сдаться и вернуться к командной строке. На саму базу ушло сорок секунд, а на то, чтобы открыть в неё окно, ушёл вечер.

Теперь умножьте это на масштаб. Приложение работает на Postgres, документы лежат в Mongo, кэш в Redis, события в ClickHouse. Четыре базы, четыре клиента, четыре набора учётных данных. В понедельник приходит новый человек, и прежде чем написать первую строчку кода, ему нужно выяснить, какие данные где лежат, найти строки подключения в вики и трёх личных чатах, дождаться доступа к VPN и поставить отдельный инструмент под каждую СУБД.

**Базы данных уже переехали.** Они перебрались в Kubernetes, в управляемые облака, в клиентские VPC, куда попадаешь только через bastion-хост. **А инструменты для чтения этих баз с ними не переехали.** Они всё ещё десктопные приложения: тяжёлые, с лицензией по числу мест, которые нужно ставить заранее, и которые исходят из того, что у вас одна база, один ноутбук и человек, который никогда не сменит рабочее место.

LibreDB Studio идёт другим путём: **инструмент идёт к данным, а не данные тащат к инструменту.**

Если отнестись к этой фразе всерьёз, она перестаёт быть предпочтением и становится техническим требованием.

- Редактор обязан работать в браузере, потому что данные не на вашей машине, и коллеги тоже не на ней.
- Он обязан открываться с телефона, потому что сбой, из-за которого нужен один запрос, не станет ждать, пока вы включите ноутбук.
- Он обязан разворачиваться как инфраструктура (контейнер, Helm chart, Operator, шаблон в один клик), потому что именно так ставится всё, что живёт рядом с базой данных.
- Он обязан встраиваться, потому что самое полезное место для редактора - внутри того продукта, который эту базу и создал.
- Он не должен ничего придерживать. Нельзя поставить инструмент с лицензией по местам и урезанными функциями в каждое окружение, которым вы управляете. **Если единый вход (SSO) стоит доплаты, инструмент перестаёт быть разворачиваемым по умолчанию.**

> MIT здесь не щедрость, а жёсткое требование самой архитектуры.

## Основные возможности

### Шестнадцать СУБД, один интерфейс

PostgreSQL · MySQL · Oracle · SQL Server · SQLite · libSQL · DuckDB · MongoDB · Redis · Couchbase · ClickHouse · Apache Druid · Elasticsearch · OpenSearch · Apache Trino · Apache Cassandra

У всех SQL-совместимых баз данных общий обозреватель схемы, ER-диаграммы, сравнение схем и панели мониторинга. Три из шестнадцати доступны только для чтения, потому что таков их собственный SQL: у Druid, Elasticsearch и OpenSearch в грамматике вообще нет `UPDATE` и `CREATE TABLE`, поэтому эти элементы управления помечены как неподдерживаемые, а не падают при попытке использования. У Druid, Elasticsearch, OpenSearch и Trino есть и второе отличие: их SQL поверх HTTP не имеет формы URI, которую это приложение умеет разбирать, поэтому подключение настраивается только через host и port, а сгенерированная миграция называет это ограничение вместо того, чтобы придумывать DDL для изменения колонок там, где в SQL этой базы данных таких выражений просто нет; то же самое касается бесхемных коллекций Couchbase. ER-диаграмма над поисковым кластером рисует только прямоугольники без связей: индекс не объявляет внешних ключей, и в модели самой базы данных их попросту нет.

| База данных | Драйвер | Возможности |
| :--- | :--- | :--- |
| **PostgreSQL** | `pg` | Полный SQL IDE, планы EXPLAIN, транзакции, отмена запроса (`pg_cancel_backend`) |
| **MySQL** | `mysql2` | Полный SQL IDE, EXPLAIN, транзакции, отмена запроса (`KILL QUERY`) |
| **Oracle** | `oracledb` (режим Thin) | Полный SQL IDE, постраничный вывод через `FETCH FIRST N ROWS`, представления мониторинга `V$`, `ANALYZE TABLE`, `ALTER INDEX REBUILD`, транзакции |
| **SQL Server** | `mssql` (tedious) | Полный SQL IDE, постраничный вывод `TOP N` / `OFFSET FETCH`, DMV `sys.dm_*`, `UPDATE STATISTICS`, `DBCC CHECKDB`, транзакции, автоопределение Azure SQL |
| **SQLite** | `bun:sqlite` / `node:sqlite` (выбирается по рантайму) | Полный SQL IDE, файловая или in-memory база (файл лежит на сервере) |
| **libSQL** | без драйвера, чистый HTTP (протокол Hrana, `POST /v2/pipeline`, порт 8080) | Полный SQL IDE для собственного сервера libSQL или Turso Cloud: тот же диалект SQLite, только по сети, а не с локального диска. Интроспекция через `EXPLAIN QUERY PLAN`, `sqlite_master` и `pragma_*`, реальный размер таблиц в байтах через `dbstat`, чего файловый драйвер выше сделать не может. Учётные данные - это auth-токен, а не пароль. Из обслуживания доступны только `REINDEX` и `PRAGMA integrity_check`: `VACUUM`, `ANALYZE`, `PRAGMA optimize` и `PRAGMA wal_checkpoint` сервер отклоняет напрямую, поэтому элементов управления для них нет |
| **DuckDB** | `@duckdb/node-api` (нативный N-API аддон, около 68 МБ бинарных файлов на платформу) | Полный SQL IDE для локального файла DuckDB или `:memory:` на том же сервере, где работает приложение. Дерево физического плана `EXPLAIN (FORMAT JSON)`, интроспекция каталога `duckdb_*`, реальный размер таблиц в байтах через распределение блоков в `pragma_storage_info`, отмена запроса через собственный `interrupt()` драйвера. Три операции обслуживания: `VACUUM`, `ANALYZE` и `CHECKPOINT`. `REINDEX` здесь ошибка синтаксиса, а `PRAGMA integrity_check` и `PRAGMA optimize` вообще не существуют, поэтому элементов управления для них нет. Нет журнала медленных запросов и списка сессий: DuckDB не публикует ни то, ни другое, и соответствующие панели честно об этом сообщают, а не показывают ноль. Файл базы допускает ровно один процесс операционной системы одновременно, даже в режиме только для чтения, поэтому второй экземпляр Studio не может открыть базу, уже занятую первым |
| **MongoDB** | `mongodb` | Редактор JSON-запросов, операции над коллекциями (find, aggregate, insert, update, delete) |
| **Couchbase** | без драйвера, чистый HTTP (Query REST + REST управления) | Полный SQL++ IDE, планы EXPLAIN, обозреватель bucket/scope/collection, вывод колонок через `INFER`, согласованность read-your-writes, обслуживание через `UPDATE STATISTICS` / `BUILD INDEX` / отмену запроса |
| **ClickHouse** | без драйвера, чистый HTTP (SQL-интерфейс, порт 8123) | Полный SQL IDE, дерево EXPLAIN в JSON, интроспекция схемы через системные таблицы, обслуживание через `OPTIMIZE TABLE` / статистику таблиц / отмену запроса |
| **Apache Druid** | без драйвера, чистый HTTP (`POST /druid/v2/sql`, порт 8888 у Router или 8082 у Broker) | SQL IDE только для чтения, дерево EXPLAIN для нативного запроса, интроспекция источников данных через `INFORMATION_SCHEMA`, мониторинг `sys.*` (сегменты, серверы, задачи загрузки). Ничто из доступного там не считается операцией обслуживания: источник данных меняется через ingestion, а не из редактора |
| **Elasticsearch** | без драйвера, чистый HTTP (`POST /_sql?format=json`, порт 9200) | SQL IDE только для чтения, обозреватель индексов и полей на основе mapping, здоровье кластера, количество документов и размер хранилища по каждому индексу. Нет EXPLAIN, нет операций обслуживания, нет панелей медленных запросов и сессий. В SQL Elasticsearch также нет `OFFSET`, поэтому вторую страницу результатов запросить нельзя - нужно сузить запрос или поднять лимит |
| **OpenSearch** | без драйвера, чистый HTTP (`POST /_plugins/_sql`, порт 9200) | Тот же обозреватель и тот же SQL IDE только для чтения, из того же модуля провайдера. Здесь работает `LIMIT n OFFSET m`, так что постраничный вывод доступен |
| **Apache Trino** | без драйвера, чистый HTTP (клиентский протокол, `POST /v1/statement`, порт 8080) | Полный SQL IDE по всем настроенным каталогам, деревья планов `EXPLAIN (FORMAT JSON)`, дерево `information_schema` для того каталога, к которому привязано подключение, мониторинг через `system.runtime` и `jmx`, реальное количество строк через `SHOW STATS`, отмена запроса и обслуживание через `kill_query`. Trino - это движок запросов, который ничего не хранит, поэтому нигде не объявляет первичные и внешние ключи и индексы: ER-диаграмма рисует прямоугольники без связей, встроенное редактирование строк выключено, а панели объёма называют каталоги вместо выдуманного размера. Неудачный запрос возвращается с HTTP 200, а пароль по обычному HTTP отклоняется, даже если на кластере отключена аутентификация |
| **Apache Cassandra** | `cassandra-driver` (чистый JavaScript, без нативных модулей) | CQL IDE через нативный протокол (порт 9042), обозреватель keyspace с отметкой ключей партиционирования и кластеризации, обзор через `system_views`, время работы и выполняющиеся запросы. Нет EXPLAIN (в CQL просто нет такого ключевого слова), нет отмены запроса (в протоколе она не предусмотрена), нет обслуживания (все операции выполняются через `nodetool`), и нет количества строк и размера: единственные цифры, которые публикует Cassandra, - это оценка партиций по уже сброшенным на диск файлам и размер в целых мебибайтах, поэтому вместо неверного числа Studio не показывает никакого |
| **Redis** | `ioredis` | Редактор команд, обозреватель ключей, мониторинг на основе INFO |

> **Безопасность транспорта работает сквозным образом, а не отдельно для каждой базы данных.** SSH-туннель открывается до того, как провайдер устанавливает соединение, и адрес подключения переписывается на локальный endpoint, поэтому это не зависит от конкретной базы: работает для любого подключения, заданного через host и port. Подключения через строку соединения (доступно для MongoDB, Couchbase, ClickHouse и libSQL) не содержат ни host, ни port, поэтому через туннель не проходят; у SQLite и DuckDB нет ни того, ни другого. Панель SSL/TLS действует везде, кроме трёх файловых баз - SQLite, DuckDB и встроенного LibreDB, - где просто нет транспорта, который можно защитить. На Trino эта настройка не опциональна: координатор отклоняет пароль по обычному HTTP. У Oracle есть особенность, о которой стоит сказать заранее: его Thin-драйвер всегда проверяет цепочку сертификатов, поэтому режиму `require` нужен CA-сертификат сервера, если сертификат самоподписанный, а строка подключения, вставленная целиком, сохраняет тот протокол, который в ней указан.

### Профессиональный SQL-редактор

- **Движок Monaco**: то же ядро, что и в VS Code.
- **Умное автодополнение**: подсказки по таблицам, колонкам и ключевым словам SQL с учётом схемы.
- **Рабочее пространство с вкладками**: параллельные задачи с независимым состоянием выполнения.
- **Визуальный EXPLAIN**: графические планы выполнения для поиска узких мест по производительности.
- **Интерактивные ER-диаграммы**: граф схемы с реальными связями по внешним ключам, метками кардинальности, миниатюрой для навигации, поиском и фильтром таблиц, компактным режимом и экспортом в PNG/SVG. Автоматическая иерархическая раскладка на ELK.js.
- **Сравнение схем и миграции**: сравнение снимков схемы или схем разных подключений бок о бок, цветовая разметка diff (добавлено/удалено/изменено) и автоматическая генерация SQL миграции для PostgreSQL, MySQL, SQLite, Oracle и SQL Server, а также изменение колонок для ClickHouse.
- **Хронология снимков**: горизонтальная временная шкала снимков схемы. Выбираете любые две точки - сразу видите разницу и то, как схема менялась со временем.

### Агент базы данных

Главная поверхность ИИ в Studio - это **панель агента** рядом с редактором; модельные помощники, перечисленные ниже, - это уже другое. Вы формулируете цель: *"в каком отделе больше всего сотрудников?"*, *"почему этот запрос выполняется медленно?"* - и нажимаете Start. Запуск составляет SQL к подключённой базе, читает результат и в конце пишет отчёт, каждое утверждение в котором ссылается на результат, из которого оно получено.

- **Только чтение, и это обеспечивает сама база, а не парсер.** Каждое выражение, которое выполняет агент, проходит через собственный аудируемый конвейер агента - решение по политике, событие аудита и учёт бюджета ещё до обращения к драйверу (`executeAuditedOperation`, `src/lib/db/operations/execution.ts:129`) - в режиме только для чтения: транзакция только для чтения на PostgreSQL, повторное подтверждение `PRAGMA query_only` перед каждым выражением на SQLite, и хендл движка `READ_ONLY` на DuckDB вместе с проверкой на уровне SQL, потому что один только этот флаг всё ещё пропускает `COPY … TO`, `EXPORT DATABASE` и табличные функции для локальных файлов. Запись и DDL отклоняются раньше, чем дойдут до базы, а `EXPLAIN ANALYZE` по умолчанию запрещён, потому что он реально выполняет выражение. Этот конвейер принадлежит только агенту: выражения, которые вы запускаете сами в редакторе, обращаются к провайдеру напрямую (`src/app/api/db/query/route.ts:44`) и таким способом не проверяются и не аудируются.
- **Режим Agent читает только PostgreSQL, SQLite и DuckDB.** Режим только для чтения зависит от самой базы, поэтому существует только там, где его реализует провайдер: `queryReadOnly` есть в `postgres.ts:915`, `sqlite.ts:537` и `duckdb/index.ts:525`, и больше нигде. На любой другой базе данных запуск в режиме Agent завершается как `engine-unsupported` (`src/lib/agent/runtime.ts:199`). Режим **Plan** доступен на любом подключении: модель там не использует никакие инструменты, ничего не выполняет и ничего не пишет в редактор, а лишь составляет выражение, которое вы можете запустить сами. Схему для контекста он получает от любой подключённой базы данных: на PostgreSQL и SQLite сервер сам составляет запросы к каталогу, а на любом другом подключении он спрашивает у собственного провайдера этого подключения описание схемы - то же самое чтение, которое уже выполняет боковая панель, и путь через режим только для чтения для этого не нужен. Так что эти два ограничения разные: режим Agent работает только с тремя базами данных, а получение схемы - со всеми, и если чтение не удаётся, запуск честно об этом сообщает, а не выдумывает таблицы.
- **Три сценария**: **Investigate** (ответить на вопрос), **Optimize** (сравнить оценочные планы, предложить индекс или переписать запрос), **Assess** (профилирование таблиц - только количества, никогда не значения).
- **Ничего не запускается само по себе.** Агент никогда не начинает выполнение за вас, не пишет в редактор и не выполняет то, что рекомендует. Применить выражение - это всегда ваш клик.
- **Либо доказательство, либо ничего.** Утверждение без ссылки на источник не может попасть в отчёт, и запуск сам формулирует итог - *"Run answered"* или *"Run did not answer"* - рядом с тем, чем он закончился.
- **С ограничениями, которые видны на экране**: 20 выражений, 60 секунд времени базы, 200 строк на одно чтение, 5 минут на весь запуск.
- **Ваша собственная модель.** Gemini (по умолчанию), OpenAI, Ollama или любой endpoint, совместимый с OpenAI. Режиму **Agent** нужна модель, умеющая вызывать инструменты - для Ollama это подтверждается реальной проверкой, а не документацией производителя. Режим **Plan** инструментов не требует и никогда не проверяется (`src/lib/agent/capability-gate.ts:74`), поэтому модель, отклонённая для режима Agent, всё ещё может использоваться в режиме Plan - это и есть то, что предложит панель.
- **Нет настроенной модели - нет ИИ.** Если нет вообще ни одной настройки `LLM_*`, панель просто не отображается, и ничего не уходит из вашей сети. Учтите, что ключ - не то же самое, что переключатель: Ollama и произвольный endpoint считаются настроенной моделью и без ключа, и тогда ИИ уже включён. Что именно отправляет агент, описано в [`docs/AGENT_DATA_FLOW.md`](docs/AGENT_DATA_FLOW.md).

Доступно только в отдельном приложении: у встраиваемого пакета `@libredb/studio` панели агента нет.
**Руководство:** [`docs/AGENT_GUIDE.md`](docs/AGENT_GUIDE.md) · **Что уходит с машины:** [`docs/AGENT_DATA_FLOW.md`](docs/AGENT_DATA_FLOW.md) · **Поведение и ограничения:** [`docs/AGENT.md`](docs/AGENT.md)

### Помощники на основе модели

- **Поддержка любой LLM**: по умолчанию Gemini, а также OpenAI, Ollama и любой endpoint, совместимый с OpenAI (LM Studio, LiteLLM, vLLM).
- **Анализ безопасности запроса**: оценка риска перед выполнением для разрушительных выражений (DELETE, DROP, TRUNCATE).
- **Объяснение запроса**: планы EXPLAIN, переведённые на обычный язык, с рекомендациями по оптимизации.
- **Учёт схемы**: схема подключённой базы передаётся как контекст, поэтому объяснение называет ваши собственные таблицы и колонки.
- **Сводка профилировщика данных**: статистика по колонкам из профилировщика, изложенная в виде текста. В этот контекст входят реальные `min` и `max` каждой колонки, то есть настоящие значения из ваших данных; см. [Agent Data Flow](docs/AGENT_DATA_FLOW.md).

### Работа с данными

- **Универсальная таблица результатов**: виртуализированный рендеринг (TanStack) для миллионов строк.
- **Редактирование прямо в таблице**: двойной клик обновляет значение на месте, но только там, где SQL этой базы данных поддерживает обновление одной строки в одной таблице; на остальных базах данных элемент управления просто скрыт.
- **Фильтры по колонкам**: текстовые фильтры по каждой колонке результата для мгновенного исследования данных.
- **Интерактивная сводная таблица**: пивот на стороне клиента с пятью функциями агрегации (COUNT, SUM, AVG, MIN, MAX) и генерацией соответствующего SQL.
- **Экспорт**: мгновенный экспорт в CSV и JSON.

### Визуализация данных

- **8 типов графиков**: столбчатые, линейные, круговые, area, точечные, гистограммы, столбчатые и area с накоплением - всё на Recharts.
- **Агрегация**: группировка с SUM, AVG, COUNT, MIN, MAX; группировка по дате с шагом час/день/неделя/месяц/год.
- **Сохранение графиков**: настройки графика сохраняются и мгновенно подгружаются заново, есть библиотека сохранённых графиков.
- **Дашборд графиков**: сетка всех сохранённых графиков для обзора данных прямо в нижней панели.

### Инструменты аналитика и разработчика

- **Профилировщик данных с ИИ**: профилирование таблицы в один клик со статистикой по колонкам (доля NULL, кардинальность, min/max, примеры значений) и текстовым описанием от модели.
- **Генератор кода ORM**: генерация интерфейсов TypeScript, схем Zod, моделей Prisma, структур Go, dataclass Python и POJO Java прямо из живой схемы таблиц.
- **Генератор тестовых данных**: генерация фейковых данных с учётом схемы и более чем 30 вариантами определения смысла колонки (email, телефон, имя, адрес и другие). На выходе - выражения INSERT или JSON для `insertMany` в MongoDB.
- **Документация базы данных**: автоматически собранный и доступный для поиска словарь данных из живой схемы, с описанием от ИИ и экспортом в Markdown.

### Аутентификация и SSO

- **Два режима аутентификации**: локальный логин/пароль или единый вход через OpenID Connect (OIDC), переключается переменной окружения.
- **Не привязан к вендору**: работает с любым провайдером, поддерживающим OIDC - Auth0, Keycloak, Okta, Azure AD, Zitadel, Google и другие.
- **Безопасность через PKCE**: Authorization Code Flow с Proof Key for Code Exchange (S256).
- **Автоматическое сопоставление ролей**: настраиваемое сопоставление ролей по claim, с точечной нотацией для вложенных claim (например, `realm_access.roles`).
- **Выход у провайдера**: выход из системы закрывает и локальную JWT-сессию, и сессию у провайдера идентификации.

### Инструменты обслуживания для DBA (только для администратора)

- **Дашборд мониторинга в реальном времени**: семь вкладок - обзор, производительность, запросы, сессии, таблицы, хранилище, пул подключений.
- **Графики трендов во времени**: метрики в реальном времени (подключения, попадания в кэш, buffer pool, deadlock) с автообновлением и историей в кольцевом буфере.
- **Настраиваемое автообновление**: интервал опроса от 5 до 60 секунд, с play/pause.
- **Оповещения по порогу**: цветовые индикаторы состояния (норма/предупреждение/критично) для попаданий в кэш, использования подключений, deadlock и заполнения buffer pool.
- **Статистика пула подключений**: метрики total/active/idle/waiting в реальном времени, с индикаторами загрузки.
- **Обслуживание в один клик**: `VACUUM`, `ANALYZE`, `REINDEX`, `UPDATE STATISTICS`, `DBCC CHECKDB`, `ALTER INDEX REBUILD` - в зависимости от базы данных.
- **Журнал аудита**: полная история всех запросов, выполненных во всей организации.

## Где проходит граница платности

Studio распространяется под MIT, потому что должна работать где угодно. Платный продукт - это libredb-platform, и продаётся в нём то, что кто-то другой берёт на себя эксплуатацию: хостинг, multi-tenancy, биллинг и поддержку. Это не функциональность, перенесённая за платную стену.

**Ни одна возможность не была перенесена на платную сторону только для того, чтобы создать повод для апгрейда.** Единый вход, RBAC, журнал аудита запросов, ER-диаграммы, функции ИИ и все NoSQL-базы данных входят в сборку MIT.

